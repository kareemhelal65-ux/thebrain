PART I — FOUNDATIONAL THESIS
1. The Multi-Agent Orchestration Thesis
The Brain AIOS is not a chatbot. It is an operating system built around a coordinated mesh of specialised AI agents — each with a defined domain, a set of tools, a memory layer, and a governance boundary. This section establishes the theoretical and architectural foundations for why multi-agent orchestration is the correct approach, and how it maps to the product's competitive position.
1.1 Why Single-Agent Systems Fail at Scale
A single LLM agent given a broad task — 'build the marketing campaign and then push the code and update the CRM' — will either attempt all sub-tasks in one context window (leading to context overflow and quality collapse) or require repeated human prompting to advance between stages. Both outcomes are unacceptable for an AI OS that is meant to reduce, not redistribute, human cognitive load.
The failure modes of monolithic AI agents are well-documented:
Context saturation: a single context window degrades in reasoning quality after approximately 4,000–8,000 tokens of active working content, regardless of the model's total context limit.
Tool overload: an agent with access to 40+ tools spends disproportionate reasoning capacity selecting tools rather than executing tasks.
Domain confusion: a marketing brief written by a code-focused agent will lack brand voice; a security audit written by a content agent will miss technical nuance.
No parallelism: a sequential monolith cannot run research while simultaneously drafting — tasks execute serially, multiplying latency.
Failure blast radius: a single agent's error cascades through the entire task. A multi-agent system contains failures within the responsible agent's boundary.
1.2 The Multi-Agent Architectural Principle
The correct architecture is a hierarchy: one Orchestrator that plans and delegates, ten Specialist Agents that execute within defined domains, and a shared memory bus that lets agents communicate state without redundant inference. This mirrors how effective human organisations work — a CEO delegates to domain leads who each own their function and report outcomes up the chain.
Core Thesis: Intelligence should be distributed across domain-specialised agents coordinated by a planning layer, not concentrated in a single generalist model. Specialisation produces better output; coordination prevents fragmentation.
The Orchestrator is not an agent itself — it is a meta-layer. It receives user intent, decomposes it into a directed acyclic graph (DAG) of sub-tasks, assigns each task to the appropriate specialist agent, manages inter-agent data flow, and assembles the final output. The Orchestrator never executes domain work; it manages.
1.3 The Ten Agents — Domain Allocation Rationale
The Brain's ten agents are not arbitrary — they map directly to the functional domains of every SMB and the highest-frequency pain points surfaced by the May 2026 market research (14 sources, Reddit, Product Hunt, industry reports). Each agent owns a domain completely: it holds the relevant tools, prompts, memory context, and output schemas for its function.

1.4 Why This Architecture Creates a Moat
A competitor can build one good agent. Replicating a coordinated mesh of ten domain-specialised agents — each trained on a company's historical data, each with its own tool registry and memory context — requires months of accumulated usage. The moat is not the technology; it is the compounding institutional knowledge stored in the graph and retrieved by each agent on every task.
PART II — SELF-LEARNING & CONTINUOUS IMPROVEMENT
2. The Self-Learning Loop: How The Brain Improves While You Sleep
The Brain is designed to be a system that compounds in value over time — not only because it accumulates more data, but because it actively learns from its own outputs, user feedback, and outcome signals. This section defines the complete self-learning architecture: the nightly improvement cycle, the feedback ingestion pipeline, the prompt evolution engine, and the safety rails that prevent runaway self-modification.
2.1 The Four-Stage Learning Cycle
The self-learning loop runs as a scheduled background process. It does not modify any model weights (fine-tuning is planned for Phase 4). Instead, it improves three things: the prompt library used by each agent, the retrieval strategy parameters (chunk size, overlap, reranker weights), and the knowledge graph's entity confidence scores. These three levers produce measurable output improvement without touching model infrastructure.
Design Principle: The Brain improves through prompt evolution, retrieval tuning, and graph enrichment — not model retraining. This keeps the improvement loop cheap, fast, and reversible.
Stage 1 — Signal Collection (Continuous, Real-Time)
Every agent interaction generates a signal. Signals are the raw material of the learning loop. The Brain collects four signal types:
Explicit feedback: user thumbs up/down on an agent output, or a written correction. Stored as a feedback_events row with the task_id, agent_id, rating, and optional correction text.
Implicit feedback: user edits the agent's draft before sending. The diff between the agent output and the final sent version is stored as a delta signal. High-delta outputs indicate systematic prompt weaknesses.
Outcome signals: whether an action item was completed, whether a drafted email received a reply, whether a generated report was used or archived. These are longer-lag signals collected via integration webhooks.
Inter-agent signals: when the Orchestrator or Sentinel rejects or corrects an agent's output before delivery to the user, the rejection reason and corrected output are stored as training pairs.
Stage 2 — Nightly Analysis (02:00 Local, Per Tenant)
At 02:00 in each tenant's configured timezone, a Celery beat job runs the learning analysis pipeline. The job is scoped per tenant — one company's feedback never influences another company's agent behaviour.
The analysis pipeline executes the following steps in sequence:
Aggregate signals from the past 7 days, grouped by agent_id and task_type.
For each agent, compute a quality score: (positive signals + implicit low-delta signals) / total signals. A score below 0.72 triggers a prompt review flag.
Cluster low-rated outputs by task_type using embedding similarity — identify whether failures are concentrated in a specific sub-task (e.g., 'the Marketing Agent consistently produces weak Instagram captions').
For each flagged cluster, retrieve the 5 lowest-rated outputs and the 5 highest-rated outputs as contrastive examples.
Call Claude Sonnet with the contrastive examples and the current agent prompt: 'Given these successful and unsuccessful outputs, identify 2-3 specific changes to this system prompt that would improve the weak outputs without degrading the strong ones. Respond in JSON: {changes: [{location, old_text, new_text, rationale}]}'.
Store the proposed prompt changes in a prompt_proposals table with status=pending_review.
Stage 3 — Shadow Testing (03:00–05:00 Local)
Proposed prompt changes are not deployed immediately. They run in shadow mode — the updated prompt is used to re-process the 10 lowest-rated tasks from the past week, and the shadow outputs are scored by a Claude Haiku judge against the originals. Only changes that improve the judge score by more than 8% are promoted to status=approved.
Safety constraint: No prompt change that increases the Sentinel rejection rate by more than 2% is ever approved, regardless of quality score improvement. Safety always wins over performance.
Stage 4 — Deployment & Rollback (05:00 Local)
Approved prompt changes are deployed to the live agent prompt library. The system maintains a full version history of every prompt change with the analysis that generated it. Admins can view the change log in the Memory Health Dashboard and roll back any change with a single click. Rollback takes effect immediately — the previous prompt version is re-activated without restarting any services.
2.2 Retrieval Strategy Auto-Tuning
Beyond prompt evolution, the learning loop also tunes retrieval parameters. The retrieval tuning job runs weekly (Sunday 04:00) and evaluates three parameters against the accumulated feedback signal:
Chunk size: tested at 384, 512, and 768 tokens. The chunk size that produces the lowest average delta (smallest user edits) for each agent's task type is selected.
Overlap: tested at 32, 64, and 128 tokens. Higher overlap improves recall on boundary-spanning concepts at the cost of storage and retrieval speed.
Reranker weight: the Cohere reranker's blend ratio between semantic similarity and BM25 keyword match is adjusted between 0.6/0.4 and 0.8/0.2. Task types with specific terminology (legal, financial) tend toward higher BM25 weight.
2.3 Knowledge Graph Confidence Scoring
Every entity in the Knowledge Graph has a confidence_score (0.0–1.0) that reflects how reliably it has been verified across multiple ingestion sources. The learning loop runs a nightly graph reconciliation job that:
Increases confidence for entities confirmed by 3+ independent source documents.
Flags entities that appear in only one source and have not been confirmed in 30+ days for admin review.
Merges near-duplicate nodes (same person referenced as 'Ahmed', 'Ahmed Mahdi', 'A. Mahdi') using fuzzy entity resolution.
Decays confidence of stale action item nodes that have not been referenced in 14+ days — surfacing them as 'possibly outdated' in agent context.
2.4 The Learning Dashboard
Admins can observe the learning loop's activity in the Memory Health Dashboard. The Learning tab shows: prompt change history with rationale, current quality scores per agent, retrieval parameter evolution over time, and upcoming shadow tests scheduled for tonight. This transparency is not optional — it is the trust layer that makes SMB owners comfortable allowing the system to self-modify.
PART III — TEMPORAL AGENT EXECUTION
3. Agents Taking Time: How The Brain Produces Perfect, Clean Output
The most common failure mode in AI-generated output is premature completion — the system produces a first-draft answer and presents it as finished work. The Brain's agents are architected around the opposite principle: every task has a minimum quality bar, and agents are given structured time and iteration budgets to reach it. This section defines the temporal execution model: how agents plan, draft, critique, revise, and self-verify before surfacing output to the user.
3.1 The Four-Phase Execution Model
Every non-trivial agent task (defined as any task with an estimated completion time > 30 seconds) follows a four-phase execution model. The phases are enforced by the Orchestrator's task runner — an agent cannot skip to Phase 4 without completing Phases 1–3.
Phase
Name
What Happens
Time Budget
Phase 1
Planning
Agent decomposes the task into sub-steps, identifies required tools and context, estimates output schema
10–20% of total budget
Phase 2
Drafting
Agent executes sub-steps sequentially, producing a raw draft output with inline annotations
40–50% of total budget
Phase 3
Critique
Agent (or judge model) scores the draft against the output schema and task requirements, identifies gaps
15–20% of total budget
Phase 4
Refinement
Agent addresses critique gaps, polishes tone and structure, validates against output schema
20–30% of total budget
Key design decision: Phase 3 is always run by a separate model invocation (not the same context window that produced the draft). This prevents the agent from 'agreeing with itself' and forces genuine critical evaluation.
3.2 The Task Budget System
Every task assigned by the Orchestrator carries a task_budget object that specifies three constraints the agent must respect:
time_budget_seconds: the maximum wall-clock time the agent has to complete the task. The Orchestrator sets this based on task complexity classification (Simple: 30s, Standard: 120s, Complex: 300s, Deep: 600s).
iteration_budget: the maximum number of Phase 3 → Phase 4 cycles before the agent must deliver its current best output. Default: 2 iterations. Complex tasks: up to 4.
quality_threshold: the minimum score (0–100) the Phase 3 critic must assign before the output is considered deliverable. Simple tasks: 70. Customer-facing outputs: 85. Compliance outputs: 95.
If an agent exhausts its iteration budget without reaching the quality threshold, it does not silently deliver a substandard output. It escalates to the Orchestrator with a structured escalation report: current quality score, identified gaps, and a recommendation (request more context from user, extend budget, or deliver with caveats clearly marked).
3.3 The Output Schema Enforcement Layer
Every agent has a defined output schema for each task type it handles. The schema is a JSON object that specifies required fields, optional fields, format constraints, and validation rules. The Phase 3 critic evaluates the draft against this schema using a structured rubric — not a free-form 'is this good?' prompt.

3.4 Asynchronous Execution & User Notification
Long-running tasks (> 60 seconds) are executed asynchronously. The user receives an immediate acknowledgment ('The Marketing Agent is working on your campaign assets — estimated completion: 4 minutes') and a progress indicator that shows the current phase. When the task completes, the user is notified via the app and optionally Slack.
The progress indicator is not a spinner — it is a structured status update that shows:
Current phase (Planning / Drafting / Critique / Refinement)
Current iteration (1 of 2)
Current quality score if in Phase 3 or 4
Estimated time remaining
User experience principle: Users should never wonder what the agent is doing. Transparency about the process builds trust and sets accurate expectations. A 4-minute wait with a visible quality score climbing from 68 to 87 feels different from a 4-minute spinner.
3.5 The Critique Model Selection
The Phase 3 critic is not always the same model that produced the draft. The Orchestrator selects the critic based on task type and cost constraints:
Simple tasks: Claude Haiku as critic. Fast, cheap, sufficient for well-defined schemas.
Standard tasks: Claude Sonnet as critic. Better reasoning for nuanced quality assessment.
Customer-facing or compliance outputs: Claude Opus as critic. Maximum reasoning quality for high-stakes output.
Code outputs: the Code Agent's linting pipeline + a Sonnet review pass. Automated validation first, then semantic review.
PART IV — INTERACTIVE CLARIFICATION PROTOCOL
4. Interactive Clarification: How The Brain Asks the Right Questions
An AI system that guesses ambiguous intent produces confident wrong answers. An AI system that asks too many questions produces friction and abandonment. The Brain's interactive clarification protocol threads the needle: it asks questions only when the answer will materially change the output, it asks only one question at a time, and it asks those questions at the right moment in the task lifecycle.
4.1 The Clarification Decision Framework
Before beginning Phase 1 of any task, the Orchestrator runs a clarification check. The check evaluates three dimensions of the incoming request:
Dimension
Clarification Triggered If...
Example
Intent ambiguity
Two or more plausible interpretations exist with different output schemas
'Create a post' — social post or blog post?
Scope ambiguity
The task boundary is undefined and scope affects execution time > 2x
'Rewrite the website' — all pages or just the homepage?
Constraint ambiguity
A required constraint (audience, tone, deadline, budget) is missing and cannot be inferred from The Brain's context
'Write a proposal' — for which client, at what budget?
If none of these three dimensions trigger, the agent proceeds without asking. The Brain infers missing non-critical context from the Knowledge Graph (if the user has previously set a default tone, a known client, or a recurring template, these are used automatically).
4.2 The One-Question Rule
When clarification is required, the system asks exactly one question per clarification round. Multiple simultaneous questions create cognitive load and reduce response rate. The Orchestrator identifies the single highest-leverage ambiguity — the one that, if resolved, would most reduce remaining uncertainty — and asks only that question.
The clarification question is not a free-text field. It is presented as a structured choice whenever possible:
Binary choice: 'Should this be formal or conversational in tone?' → [Formal] [Conversational]
Multi-select: 'Which platforms should this campaign target?' → [Instagram] [LinkedIn] [Email] [All three]
Free text (last resort): used only when the answer space cannot be enumerated, e.g., 'What is the name of the client this proposal is for?'
Principle: Structured choices are answered faster, are less ambiguous to parse, and produce better downstream task inputs. Free text is only used when structure would feel unnatural or limiting.
4.3 When Clarification Interrupts vs. When It Doesn't
The clarification check timing depends on task complexity and user availability signals:
Scenario

Rationale

4.4 Context-Inferred Defaults
Before asking a clarification question, the Orchestrator always checks The Brain's context layer for inferred defaults. If the answer can be derived from company history with > 80% confidence, the assumption is used silently and logged — not asked.
Examples of context-inferred defaults:
Tone: if the company has approved 50+ formal emails and 3 casual ones, the default tone is formal without asking.
Audience: if the task is tagged with a client name that exists as a Person node in the graph, audience demographics are pulled from the CRM context automatically.
Format: if the user always requests Google Docs output, the agent defaults to that format.
Brand: if a brand guidelines document has been ingested, colour palette, font, and voice are always inferred — never asked.
4.5 The Clarification History
Every clarification Q&A pair is stored in the Knowledge Graph as a UserPreference node linked to the requesting user and task type. Over time, this creates a personal preference model that eliminates recurring questions. After the third time a user answers the same type of clarification question the same way, the system learns the preference and stops asking.
PART V — THE TEN AGENTS: FULL TECHNICAL SPECIFICATIONS
5. Building Each Agent: Complete Technical Specifications
This section provides the complete technical specification for each of the ten agents — covering system prompt architecture, tool registry, output schemas, capability map, and MVP build steps. Each agent is designed to be a production-quality specialist, not a prototype.
5.1 The Orchestrator Agent
Role: The Orchestrator is the brain of the brain. It receives user intent, builds a task execution plan, delegates to specialists, and assembles the final response. It never executes domain work.
System Prompt Architecture
The Orchestrator's system prompt is structured in four sections: Role Definition, Task Decomposition Rules, Agent Registry, and Output Format Specification. The role definition establishes that the Orchestrator is a meta-planner that must never attempt to produce domain content — if it receives a request to write a marketing email, it must delegate to the Marketing Agent, not attempt the task itself.
Tool Registry
task_assign(agent_id, task_description, context_bundle, budget) — dispatches a task to a specialist agent
get_task_status(task_id) — polls agent task state
assemble_response(task_results[]) — merges multiple agent outputs into a coherent user response
clarification_request(question, options[]) — triggers the clarification protocol
escalate_to_sentinel(task_id, reason) — routes sensitive tasks through approval
Task DAG Construction
For multi-agent tasks, the Orchestrator builds a directed acyclic graph (DAG) of sub-tasks. Each node is an agent assignment. Edges represent dependencies — a node cannot begin until all its parent nodes are complete. Independent nodes execute in parallel via Celery's concurrent worker pool.
MVP Build Steps
Implement task_assign as a Celery task dispatch function with Redis task state tracking.
Build the LLM planner prompt that converts user intent into a JSON task list with agent_id, task_description, dependencies, and budget per task.
Implement DAG executor: topological sort of tasks, parallel dispatch of independent nodes, sequential execution of dependent nodes.
Build assemble_response: takes a list of task_result objects and produces a unified markdown response with source attributions.

5.4 The Research Agent
Role: Synthesises information from The Brain's internal knowledge base and external web sources. Produces structured research reports, competitive analyses, market summaries, and fact-checked answers with citations.
Hybrid Retrieval Architecture
The Research Agent uses a three-source retrieval strategy, ranked by retrieval priority:
Priority 1 — Internal Brain context: pgvector semantic search + Knowledge Graph traversal. Company-specific facts, past decisions, internal documents. Always searched first.
Priority 2 — Cached external data: previously retrieved and stored web content in the Brain's document store. Avoids redundant API calls for recently accessed information.
Priority 3 — Live web search: called only when internal context is insufficient (confidence < 70%) or the query explicitly requires current information (news, pricing, statistics).
Citation Architecture
Every claim in a Research Agent output is linked to a source citation. Citations are stored as citation_nodes in the Knowledge Graph, linked to the document or web page they reference. The output format includes inline citation markers ([1], [2]) and a structured reference list at the end. Citations are never fabricated — if a claim cannot be sourced, it is marked as [UNVERIFIED] and flagged for human review.
MVP Build Steps
Build Research Agent system prompt with citation enforcement rules and output schema (summary, sections, citations, confidence_score).
Implement hybrid retrieval tool: internal Brain search first, web search fallback, with confidence scoring.
Build citation linker: maps each claim in the output to its source, generates reference list, flags unverifiable claims.

5.7 The Finance Agent
Role: Produces financial reports, cash flow forecasts, invoice tracking summaries, and budget analysis. All financial outputs are marked as AI-generated and require human review before any financial decision is made.
Compliance Guardrails
The Finance Agent has the most restrictive Sentinel guardrails of any agent:
All outputs are watermarked: 'AI-generated financial analysis — not a substitute for professional financial advice. Review required before any financial decision.'
No agent can initiate any payment, transfer, or financial commitment — these actions are categorically blocked.
All Finance Agent outputs go through Sentinel's approval queue before delivery, regardless of task complexity.
Numerical claims are sourced exclusively from ingested financial documents — the agent is prohibited from generating placeholder numbers.
MVP Build Steps
Build Finance Agent system prompt with compliance watermark enforcement and source-only numerical claim rules.
Implement QuickBooks API integration: fetch invoices, expenses, and P&L data.
Build cash flow report generator: structured output with timeline, categorised inflows/outflows, and net position.
Wire all Finance Agent tasks through Sentinel approval queue.

Role: Curates and maintains The Brain's knowledge base. Runs ingestion, entity extraction, graph enrichment, confidence scoring, and memory health analysis. The Memory Agent is the custodian of The Brain's long-term intelligence.

Ingestion orchestration: triggers re-ingestion when integration webhooks fire new content.
Entity extraction: runs spaCy NER pass + Claude Haiku structured extraction for Decision, ActionItem, and Topic entities.
Graph enrichment: upserts new nodes and edges, merges duplicates, updates confidence scores.
Memory health scoring: computes the nightly Memory Health Score across coverage, freshness, density, and gap detection dimensions.
Memory curation: surfaces low-confidence or stale entities to admins for review or deletion.
MVP Build Steps
Build Memory Agent as a set of Celery tasks triggered by integration webhooks and scheduled beat jobs.
Implement entity extraction pipeline: spaCy NER → Claude Haiku structured extraction → graph upsert.
Build Memory Health Score calculator as a nightly Celery beat job.
Create Memory Health Dashboard API endpoints consumed by the Next.js admin UI.
5.10 The Sentinel Agent
Role: Governs all agent actions that write to external systems, handles PII detection and redaction, maintains the HMAC-signed audit log, and manages the human approval queue. Nothing writes outside The Brain without Sentinel's clearance.
The Write Gate
Every agent action that writes to an external system — sending an email, creating a PR, updating a CRM record, posting to Slack — must pass through Sentinel's write gate. The write gate evaluates:
Action classification: is this action reversible? Irreversible actions (sent emails, published posts) require explicit approval.
Scope check: does the action affect more than 5 records? Bulk actions always require approval regardless of reversibility.
PII check: does the output contain unmasked PII going to an unauthorised recipient?
Anomaly check: is this action unusual for this tenant (e.g., sending to a new domain not previously used)?
The Approval Queue
Actions that fail the write gate are held in the approval_queue table. Users see pending approvals on their dashboard with: a plain-language description of the action, a diff view showing exactly what will be written, source attribution (which agent, which task, which user request), and Approve / Reject / Edit buttons. Approved actions execute immediately; rejected actions are logged with the rejection reason and the agent is notified to revise if appropriate.
MVP Build Steps
Implement write gate function: evaluates action against the four criteria, returns ALLOW / HOLD / BLOCK with reason.
Build approval queue: database table, FastAPI endpoints, Next.js UI with diff viewer.
Implement HMAC-SHA256 audit log: each entry signed with per-tenant key, daily chain hash computed.
Build PII scanner using Microsoft Presidio: configurable entity types, three treatment modes (redact, mask, passthrough).

6.2 The Shared Context Bundle
When the Orchestrator assigns a task to a specialist agent, it packages a context_bundle — a structured JSON object that contains everything the agent needs to begin work without additional retrieval:
user_intent: the original user request, verbatim
task_description: the specific sub-task assigned to this agent, decomposed from the intent
brain_context: top-5 semantic retrieval results relevant to this task, pre-fetched by the Orchestrator
graph_context: 1-hop graph neighbours for key entities mentioned in the task
agent_history: the last 3 outputs from this same agent for this same tenant (for style and format consistency)
dependent_outputs: the results of any upstream agent tasks this task depends on
budget: time_budget_seconds, iteration_budget, quality_threshold
The context bundle is serialised to JSON and stored in Redis with a TTL of 2 hours. The agent retrieves it at task start — this eliminates redundant Brain queries during execution.
6.3 Parallel vs. Sequential Execution
The Orchestrator's DAG executor distinguishes between tasks that can run in parallel and tasks that must run sequentially. The rule is simple: if Task B needs the output of Task A, it is sequential. If Task B and Task C both only need the original context bundle, they run in parallel.
Parallelism is implemented via Celery's concurrent worker pool. The default pool size is 4 concurrent agents per tenant (expandable in the Cortex tier). The Orchestrator dispatches all independent DAG nodes simultaneously and polls for completion via Redis task state before assembling the final response.
6.4 Worked Example 1: Building a Marketing Website
User request: 'Build a landing page for our new product launch — the Neural tier of The Brain.'
This request requires the Research Agent (competitive landscape), the Marketing Agent (copy and assets), and the Code Agent (HTML/React implementation). The Orchestrator coordinates all three.
Step-by-Step Execution
Orchestrator receives request. Runs clarification check: scope is clear, brand guidelines in Brain, target audience inferable. No clarification needed.
Orchestrator builds DAG: Task A (Research Agent — competitive analysis, 120s) → Task B (Marketing Agent — copy and asset brief, 180s) → Task C (Code Agent — React landing page, 300s). B and C are sequential to A; C is sequential to B.
Task A dispatched to Research Agent with context bundle. Research Agent retrieves Brain context on Neural tier, runs web search for competitor landing pages, produces structured competitive brief (positioning, differentiators, pricing table).
Task A completes. Orchestrator places competitive brief in Task B's context bundle as a dependent_output.
Task B dispatched to Marketing Agent. Agent reads competitive brief, retrieves brand guidelines from Brain, produces: hero copy, feature section copy, pricing section copy, CTA copy, and 3 visual asset briefs. Image generation API called for hero banner PNG (1920x1080) and feature icon set (512x512 each). All assets stored in S3.
Task B completes. Marketing Agent output (copy + S3 asset URLs) placed in Task C's context bundle.
Task C dispatched to Code Agent. Agent generates Next.js landing page component using the copy and referencing the S3 asset URLs. Code executed in sandbox to verify no runtime errors. Code Agent creates a GitHub PR in the tenant's repository with title 'feat: Neural tier landing page' and a description summarising the copy sources and asset links.
Task C completes. Orchestrator assembles final response: PR link, preview of the copy, S3 links to visual assets, and a summary of the competitive positioning used.
Sentinel write gate triggered for the GitHub PR creation. PR creation is reversible (can be closed). Auto-approved per tenant config. PR is created.
User receives: 'Your Neural tier landing page is ready. PR #52 has been created in brain-web. The hero banner PNG is attached. The page uses the competitive positioning angle of cross-stack memory vs. session-only tools.'
6.5 Worked Example 2: GitHub Code Review + Documentation Update
User request: 'Review PR #47 in brain-api and update the README with any new endpoints.'
This request requires the Code Agent (review PR #47) and the Research Agent (read existing README + new endpoints). The two tasks are partially parallel.
Step-by-Step Execution
Orchestrator builds DAG: Task A (Code Agent — fetch PR diff + run review, 90s) runs in parallel with Task B (Research Agent — fetch current README and endpoint documentation, 60s). Task C (Code Agent — update README with new endpoints, 120s) is sequential to both A and B.
Tasks A and B dispatched simultaneously to their respective agents.
Task B (Research Agent) fetches README from GitHub, extracts documented endpoint list, retrieves any existing API documentation from The Brain. Completes in ~45 seconds.
Task A (Code Agent) fetches PR diff, runs Pylint on changed files, calls Claude Sonnet review prompt. Identifies 2 critical issues (missing input validation on /brain/query endpoint), 3 warnings, 4 suggestions. Posts review comments to PR via GitHub API. Completes in ~85 seconds.
Both tasks complete. Orchestrator places both outputs in Task C's context bundle: the code review output (which lists new endpoints added in the PR) and the Research Agent's current README analysis.
Task C dispatched to Code Agent. Agent identifies that the PR adds 2 new endpoints not documented in the README: POST /brain/query/batch and GET /health/detailed. Agent generates README additions: endpoint description, parameters table, example request/response for each new endpoint. Formats additions in the existing README style (retrieved from the Research Agent output).
Sentinel write gate triggered: README update is a GitHub commit. Reversible. Auto-approved. Commit pushed to the PR branch.
User receives: 'PR #47 reviewed — 2 critical issues flagged, review posted. README updated with 2 new endpoints (POST /brain/query/batch and GET /health/detailed). All changes are in the PR branch.'
6.6 Agent Failure Handling & Circuit Breaking
When an agent fails mid-task (timeout, API error, quality threshold not met after max iterations), the Orchestrator does not silently fail or retry infinitely. It applies a circuit-breaking strategy:
First failure: retry once with a fresh context bundle (clears any corrupted intermediate state).
Second failure: attempt with a fallback model (if the primary was Sonnet, retry with Opus; if Opus fails, escalate).
Third failure: mark the task as FAILED, notify the user with the failure reason and the partial output achieved, and log the failure chain for the learning loop.
Partial outputs are always preserved. If the Marketing Agent completed copy but failed on image generation, the copy is delivered with a note that the image generation will be retried automatically when the API recovers.

7.4 MVP Temporal Execution — The Quality Bar
The full 4-phase execution model ships in Phase 2. The MVP implements a simplified 2-phase model for the meeting query and summary pipeline:
Phase 1 — Draft: the primary LLM call produces the response. Prompt instructs the model to think step-by-step before writing the final answer (Chain-of-Thought elicitation within a single call).
Phase 2 — Self-check: a second lightweight Claude Haiku call evaluates the draft: 'Does this answer directly address the question? Is every claim sourced from the context provided? Is any claim uncertain or potentially incorrect?' If the self-check flags issues, the response is regenerated with the specific flags as additional constraints.
This 2-phase approach adds ~400ms of latency (Haiku is fast) but meaningfully improves answer quality and citation accuracy — directly relevant to the demo's 3-second response target (the overhead is within budget).
7.5 MVP Interactive Clarification — One Question Protocol
The full clarification framework ships in Phase 2. The MVP implements the one-question protocol for meeting queries only:
Before the Orchestrator routes a meeting query, it checks for scope ambiguity: if the query contains a time reference ('last month', 'Q1', 'recently') that maps to more than 20 meetings in the database, it asks: 'I found [N] meetings in that period. Should I search all of them, or would you like to narrow to a specific project or person?' with structured [All meetings] [Narrow by person] [Narrow by project] buttons.
This single clarification check meaningfully improves retrieval precision on the most common source of poor answers (overly broad time-range queries) without adding friction to precise queries.

8.3 Security Architecture Decisions
The following security decisions are non-negotiable across all phases and must be implemented from Week 1:
Tenant isolation: every database query, every embedding retrieval, every graph query is filtered by tenant_id. No cross-tenant data leakage is architecturally possible — not dependent on application logic alone.
Write gate: no agent writes to any external system without passing through the Sentinel write gate. This is enforced at the function call level, not the prompt level.
API key management: all external API keys (GitHub, HubSpot, QuickBooks) are stored in Supabase Vault (MVP) and AWS Secrets Manager (production). Never in environment variables in the codebase.
PII scanning: Microsoft Presidio runs on all ingested content before storage. PII entities are tagged in metadata but not stored in plaintext embeddings.
Audit logging: every agent action, every Sentinel decision, every user approval is logged with timestamp, tenant_id, user_id, action_type, and payload hash. Log entries are immutable once written.
